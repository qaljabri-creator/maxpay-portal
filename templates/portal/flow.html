{% load i18n %} {% comment %} The client request flow (spec §7) — build-order step 6. Six screens, one document. They cannot be six pages: the portal is framed cross-site, Django's CSRF cookie never arrives, and the per-session token that stands in for it can only travel in a header — which only `fetch` can set. See apps/portal/flow_views.py. Every screen is present in the DOM from the start and shown by `data-screen` on the shell, so moving between them costs no request and no reflow of the frame. The lists inside them are built by static/js/flow.js from the JSON endpoints; what is written here is the furniture, so the markup stays readable and the script stays free of layout. No inline script, no inline style, no inline handler — the CSP shipped with this page is `default-src 'self'` and each of those would need it relaxed. Step 10 added the withdrawal direction to the same six screens rather than a second set of them: screens 1 to 3 are identical, and screen 4 swaps the wallet-to-pay-into block and the proof upload for a destination account. Both halves are in the DOM here and the script shows whichever the `needs` object in the options payload says this direction uses — the server decides, so the form can never collect a field the submission would refuse. {% endcomment %}
